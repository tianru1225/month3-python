# ADR-001：Service 负责业务事务边界

- 状态：Accepted
- 日期：2026-09-22

## 背景

项目中的一个业务动作可能包含多次数据库写入。如果 Repository 在每次写入后自行 `commit()`，中途失败就可能留下半成品。当前项目没有跨数据库和分布式事务需求，因此采用简单、可解释的本地事务边界。

## 决策

1. Repository 负责查询、创建对象和必要的 `flush()`，不负责 `commit()`。
2. Service 负责业务校验，并在业务动作成功后调用一次 `commit()`。
3. Service 在需要转换业务异常时回滚；数据库异常向上抛出前也结束当前失败事务。
4. Service 提交后按需要 `refresh()`，返回数据库已确认的对象。
5. 一个业务动作包含的多次写入使用同一个 Session 和同一个事务。
6. Day139 的重排提案和审计事件在同一事务中提交，提案未确认前不能直接发布计划。
7. 任务状态转换继续使用现有条件更新和状态机规则，不额外引入锁或重试框架。

## 不采用的方案

当前不增加通用 Unit of Work、事务装饰器、Saga、事件总线、消息队列、分布式事务、并发锁或自动重试。它们解决的是当前项目尚未遇到的跨服务、跨数据库或高并发问题，会增加学习和维护成本。

## 影响

Repository 可以被多个 Service 复用，且不会偷偷提交不完整的数据。Service 的成功路径和失败路径更容易测试。回滚只影响当前尚未提交的事务；已经提交的历史记录不会被回滚。

## 验证方式

通过故障注入测试验证计划、计划版本、任务、任务前置关系和任务状态转换的失败回滚。Day139 的重排提案和审计事件继续由 `tests/test_replan_audit.py` 验证。通过 PostgreSQL 迁移验收确认正式数据库结构与模型一致。
