# 资料驱动学习计划领域契约

> 状态：已冻结
>
> 决策日期：2026-08-21
>
> 适用范围：Day121-Day145 学习平台最小纵向闭环

## 1. 产品核心闭环

第一版产品必须围绕用户自己的学习资料工作：

~~~text
注册并登录
-> 创建学习项目
-> 上传 Markdown、TXT 或文本型 PDF
-> 校验并解析资料
-> 资料达到 READY
-> 根据 READY 资料生成计划草案
-> 用户查看并确认草案
-> 发布正式计划
-> 完成学习任务
-> 提交文本答案或测试报告
-> 更新任务状态和基础掌握度
~~~

正式学习计划不是脱离资料的通用聊天结果。模型可以帮助整理和拆解资料，但计划必须能够追溯到实际使用的资料版本。

## 2. 第一版支持范围

第一版只支持以下三种资料格式：

| 格式 | 规范值 | 第一版要求 |
| --- | --- | --- |
| Markdown | markdown | 保留标题层级、章节关系和代码块；支持常见 .md 文件 |
| 纯文本 | txt | 保留原始文本顺序、行内容和必要的行定位；支持 .txt 文件 |
| 文本型 PDF | text_pdf | 必须存在文本层，并保留页码定位；支持可提取文本的 .pdf 文件 |

TXT 必须保留在第一版范围内。它不需要额外的复杂依赖，是最简单的资料上传和解析路径，适合验证“上传 -> READY -> 计划 -> 任务”的完整闭环。

第一版明确不支持：

- 扫描型 PDF；
- 没有文本层的 PDF；
- 需要 OCR 才能读取的资料；
- DOCX、PPTX、表格文件；
- 网页 URL、Git 仓库和自动联网搜索；
- 平台内置模板作为正式计划来源；
- 没有用户资料时生成正式学习计划。

不支持的格式必须返回明确的业务错误，不能静默当作空文本，也不能继续进入 READY。

## 3. 资料实体必须表达的事实

后续 Material 模型至少需要能够表达：

- 所属用户；
- 所属学习项目；
- 原始文件名；
- 规范化后的格式值；
- MIME 类型；
- 文件大小；
- 内容哈希；
- 安全存储位置或对象标识；
- 上传时间；
- 解析器名称和版本；
- 当前处理状态；
- 解析后的内容摘要或内容存储位置；
- 来源定位信息；
- 失败时的公开业务错误码。

原始文件和解析结果要能区分。重新解析不能伪造新的原始文件，也不能覆盖已经被历史计划引用的解析版本。

## 4. 资料处理状态

资料处理状态至少需要支持以下业务过程：

~~~text
UPLOADED -> QUEUED -> PARSING -> READY
                              -> FAILED
~~~

状态含义：

- UPLOADED：文件已经通过上传层的基本校验并保存；
- QUEUED：解析任务已经进入后台队列；
- PARSING：解析器正在处理；
- READY：解析成功，内容非空，来源定位可用；
- FAILED：解析失败、格式不支持、内容为空或无法满足安全边界。

READY 不是“文件存在”的别名。只有解析完成、内容非空且来源定位可用，资料才可以成为计划生成输入。

失败资料可以重新上传、重新排队或被替换，但失败状态不能被当作 READY 使用。扫描型 PDF 和损坏 PDF 不得因为文件扩展名正确就进入 READY。

## 5. 资料可用门禁

正式计划生成前必须同时满足：

1. 学习项目属于当前登录用户；
2. 项目至少关联一份属于该用户和该项目的资料；
3. 资料格式属于 markdown、txt 或 text_pdf；
4. 资料处理状态为 READY；
5. 解析后的内容非空；
6. 资料来源定位信息可用；
7. 计划生成请求记录实际使用的资料 ID 和版本；
8. 用户确认前只能产生计划草案，不能直接发布正式计划。

没有 READY 资料时，服务必须在调用 Provider 前返回明确的业务错误，不得使用项目目标、默认模板或模型常识替代资料。

## 6. 计划草案和正式计划

模型根据已选资料生成的结果首先是计划草案。草案至少需要保存：

- 关联项目；
- 使用的资料 ID；
- 使用的资料版本或内容哈希；
- 生成时间；
- Provider 和模型标识；
- 结构化计划内容；
- 用户确认状态；
- 公开的来源证明。

计划草案必须经过用户显式确认，才能发布为正式计划。模型不能替用户确认，后台任务不能自动发布。

本阶段的确认采用最小充分实现：

- 页面展示完整计划草案；
- 用户检查目标、时间安排、任务内容和来源证明；
- 用户点击一次“确认并发布”或同等含义的明确操作；
- 后端将该草案从 `DRAFT` 转为 `PUBLISHED`；
- 发布后才能生成或激活正式任务；
- 不实现逐条审批、多人审批、复杂编辑器或额外审核流。

“确认并发布”不是复杂审批系统，而是用户对模型生成结果承担最终确认的最小控制点。用户不确认时，草案可以继续查看、修改或重新生成，但不能被当作正式计划执行。

正式计划至少需要能够追溯到：

- 资料 ID；
- 资料版本或内容哈希；
- 文件名；
- Markdown 的标题或章节定位；
- TXT 的行或文本偏移定位；
- PDF 的页码和必要的文本片段定位；
- 生成所用模型和时间。

来源证明必须指向真实资料。系统不得生成不存在的文件名、页码、章节、行号、URL 或引用片段。

## 7. 计划版本边界

已发布计划是用户确认过的历史事实，不能被新资料静默覆盖。

后续新增、替换或重新解析资料时：

- 不得直接改写已发布计划的来源证明；
- 不得直接把旧计划标记为来自新资料；
- 可以生成新的计划草案或重排提案；
- 新草案必须记录新的资料版本；
- 只有用户确认并发布新版本后，新的计划才成为当前正式计划；
- 生成失败或用户拒绝时，原正式计划继续有效。

## 8. 用户所有权和越权边界

后续所有项目、资料、计划、任务和证据查询都必须按当前 JWT 用户隔离。

- 用户不能读取其他用户的项目或资料；
- 用户不能把其他用户的资料绑定到自己的项目；
- 用户不能通过猜测 ID 访问其他用户的计划、任务或证据；
- 资料来源证明不能泄漏其他用户的文件名、路径或内容；
- API Key 不能替代 JWT 访问用户业务资源。

## 9. 本阶段明确不做

Day121-Day145 当前最小闭环不实现：

- OCR；
- 向量检索、混合检索和 Reranker；
- 自动 Agent 规划和工具循环；
- 无资料正式计划；
- 平台模板市场；
- 自动联网搜索；
- DOCX、PPTX、网页和 Git 仓库解析；
- 多用户协作和组织权限；
- 复杂的版本合并；
- 自动覆盖已发布计划；
- 模型直接改变正式任务状态；
- refresh token、SSO 和其他与本日领域边界无关的认证扩展。

这些能力不是永久否定，而是当前 MVP 不提前实现。出现真实需求时单独做产品决策。

## 10. Day121-Day145 范围冻结

本阶段只实现以下纵向闭环：

~~~text
创建项目
-> 上传支持格式资料
-> 异步解析并查询状态
-> READY 门禁
-> 生成计划草案
-> 用户确认并发布计划
-> 查询今日任务
-> 完成任务
-> 提交证据
-> 按规则更新任务状态
~~~

本阶段的正式计划必须来自用户上传并成功解析为 READY 的资料。模板、无资料草案、OCR 和检索能力不进入当前闭环。

## 11. 后续日期的实现约束

- Day122：确定用户、项目、资料、资料版本、计划、计划版本、任务和证据的关系；
- Day123：实现学习项目模型，不提前实现资料上传；
- Day124：实现当前用户项目创建、列表和详情，并覆盖越权；
- Day125：实现资料模型、格式值、状态值、哈希和来源定位字段；
- Day126：实现上传校验，拒绝危险文件名、超限文件和不支持格式；
- Day127：分别实现 Markdown、TXT 和文本型 PDF 提取，并保留来源定位；
- Day128：实现 READY 门禁，空资料、失败资料和扫描型 PDF 不能生成计划；
- Day129：实现项目资料绑定、解绑、幂等和历史来源保护；
- Day130：复用 RQ 处理资料任务，PostgreSQL 保存长期业务状态；
- Day131-Day145：完成计划草案、一次确认发布、任务、证据和真实资料驱动的纵向闭环。

后续实现可以调整内部模块位置，但不能改变本日冻结的支持格式、READY 门禁、来源证明、用户确认和历史计划版本规则。

## 12. 决策结论

第一版支持 Markdown、TXT 和文本型 PDF。TXT 保留，因为实现成本低、没有额外解析复杂度，并且适合最早验证完整产品闭环。

第一版正式学习计划必须基于用户提供且成功解析为 READY 的资料。没有 READY 资料时不得生成或发布正式计划；解析失败、空内容和扫描型 PDF 不得绕过门禁；计划草案必须经过用户确认；已发布计划不得被新资料静默覆盖。
